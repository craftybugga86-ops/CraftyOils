# Security Review

**Date:** 2026-09-13

**Scope reviewed:** Full repository (web game: `index.html`, `dig-grid.html`, `css/`, `js/`; Android wrapper: `android/app/src/main/java/com/craftyoils/app/MainActivity.java`, `AndroidManifest.xml`; CI: `.github/workflows/build-android-apk.yml`). No base branch exists to diff against (this branch is the repository's entire history), so the full tree was reviewed as the change set.

**Result: No HIGH or MEDIUM confidence findings.**

## Notes from the review (none rose to reportable severity)

- **Web game (`js/database.js`, `js/dig-grid.js`, `js/title.js`):** The only external-data ingestion point is Import Database (`Database.importFile`), which `JSON.parse`s a user-selected local file. All fields are coerced through `Number(...) || 0` / `!!(...)` and rebuilt into clean objects before any DOM write; player-facing strings (labels, icons) always come from hardcoded constants (`PLAYER_LABELS`, `TYPE_INFO`), never from the imported file. No `innerHTML` write includes attacker-influenced text. No `eval`, `Function`, or `document.write` anywhere.
- **`js/error-banner.js`:** Renders caught error messages via `textContent`, not `innerHTML` — safe even though the message text is only partially controlled.
- **Android WebView (`MainActivity.java`):** Loads a single hardcoded `file:///android_asset/index.html` — not derived from any `Intent` extra, deep link, or external caller, so there's no way for another app to redirect it to attacker-controlled content. No `addJavascriptInterface()` is used, so JavaScript has no bridge into Java code despite JS being enabled. No `INTERNET` permission is requested at all, so even an unexpected external link in the WebView cannot reach the network.
- **`.github/workflows/build-android-apk.yml`:** This is the only component with elevated privilege (`contents: write`, and a step that runs `git push`). Its triggers are `workflow_dispatch` and `push` to `main`/`master` only — there is no `pull_request`/`pull_request_target` trigger, so it can't be invoked by an untrusted fork PR. Anyone able to trigger it already has push access to the repo, so granting it write permissions doesn't cross a trust boundary. The commit/push step uses only a fixed, hardcoded output path — no external data is interpolated into the shell commands.

No code changes were made as a result of the initial review above; see the addendum below for a follow-up reassessment that did result in one fix.

## Addendum: reassessment against known browser/WebView CVEs

Prompted by a follow-up request to specifically weigh known browser CVEs, since Android's `WebView` is a Chromium-based rendering engine that inherits Chromium's vulnerability history.

**Current, real CVEs exist in this exact component.** A live search turned up several 2026 Chromium/Android-WebView CVEs, including use-after-free bugs enabling code execution inside the sandbox (e.g. CVE-2026-13037), a privilege-escalation bug (CVE-2026-12448), and cross-origin data-leak bugs (CVE-2026-11097, CVE-2026-11007) — the same *class* of bug (cross-origin leak) that prior CVEs (CVE-2023-2033, CVE-2025-10284) saw used in the wild to steal credentials from banking and email apps. This is not a theoretical category — it's actively disclosed and patched on an ongoing basis.

**Why this app's exposure is structurally limited, not just patched-and-hope:** almost every one of the above CVE classes requires the WebView to load and render *attacker-influenced* content — a malicious webpage, a cross-origin resource, a crafted deep link — to trigger the vulnerable code path. This app:
- requests no `INTERNET` permission, so it cannot fetch or render any remote content at all;
- never calls `loadUrl()` with anything other than the one hardcoded `file:///android_asset/index.html` path — not derived from an `Intent`, deep link, or any other external input;
- uses no `addJavascriptInterface()`, so there's no JS-to-Java bridge to abuse even with JavaScript enabled;
- only ever has a single origin loaded (its own bundled assets) — cross-origin leak bugs need a second, attacker-controlled origin to leak *from*, which never exists here.

So while the underlying Chromium engine on a given device may well contain unpatched CVEs at any point in time (as any browser engine does), this app gives that engine nothing to exploit them with — there is no delivery vector for attacker-controlled content to ever reach the WebView.

**One gap found and fixed:** `MainActivity.java` called `setAllowFileAccess(true)`. Android's own WebView security guidance ([WebViews – Unsafe File Inclusion](https://developer.android.com/privacy-and-security/risks/webview-unsafe-file-inclusion)) recommends apps that only load bundled assets explicitly set `setAllowFileAccess(false)`, `setAllowContentAccess(false)`, `setAllowFileAccessFromFileURLs(false)`, and `setAllowUniversalAccessFromFileURLs(false)` — the last two already default to `false` since API 16/30, but the first two do not. `file:///android_asset/` and `file:///android_res/` (the only paths this app loads) remain reachable regardless of these settings, confirmed against Android's WebView documentation, so this required no behavior change to the app. **Fixed** in `MainActivity.java`: all four now explicitly disabled. Given the app's minSdk (21) and targetSdk (34) span old and new WebView default behavior, doing this explicitly removes any dependency on which OS version's defaults happen to apply.

This was low severity on its own (no current delivery vector makes it reachable), but cheap, safe to apply, and closes off an entire documented risk class before any future code change could accidentally open a delivery vector (e.g. adding a second `loadUrl()` call, an external link, or a deep-link handler) without anyone revisiting this setting.

**Residual/operational note (not a code fix):** Android System WebView is updated independently of this app via Google Play on devices with Play Services, so most devices receive Chromium security patches on their own cadence. Devices without Play Services (or with updates disabled) may run an outdated, unpatched WebView build — a device/OS-level risk this app's code cannot mitigate directly, beyond minimizing what the WebView is ever asked to render, as above.
